# v2 实现 · 镜头组通用说明

《余光 AFTERGLOW》4:10 · 24 fps · 6000 帧 · 1920×1080 · 2.39:1 遮幅（有效画面 y = 138→942）。每一帧都由代码渲染：Three.js r180，跑在无头 Chromium 的 SwiftShader（CPU）里。目标是戛纳级短片：每一帧都要像精心拍摄或精心制作的视效画面，不能是“程序员美术”。

## 依据（按优先级）

1. `docs/v2/brief.md`：用户的任务书。
2. `docs/v2/screenplay-v2.md`：唯一的时间与内容依据。你段落的节拍要全部读完，另外读 §0 全片常量与约定、§5 贯穿规则、§9、文末各段补记与“定案”。
3. `docs/v2/shotlist-v2.md`：你段落的镜头行，写了机位、视线、前中后景、光源、坐标。
4. `docs/v2/visual-changes-v2.md`：
   - 第一部分是全片规范：三级明暗、按材质的色彩、泛光、字号、主体尺度。
   - 第二部分是你段落的“沿用 / 修改 / 新增 / 检查点 K-n / 预算”。**检查点就是验收标准。**
5. `docs/v2/timeline-v2.md`：你段落的事件帧。
6. `docs/v2/audit-current.md`：现状证据与工程约束。
7. `docs/engine.md`：引擎契约与 v2 新接口，包括 handoff、postBlend、`motionBlur(f)`、`ctx.range`、bloomMask，以及交接帧约定。

剧本已经定案。实现中如果发现剧本有技术上做不到、或做出来会显得廉价的地方，选最接近剧本意图的高级解法，并写进最终报告；不要自行改时间。

## 引擎契约（要点）

- 模块文件是 `web/src/shots/<module>.js`，辅助文件放 `web/src/shots/<module>/`。
- 模块导出 `export async function create(ctx)`，返回 `{ render(shot, f), post?(shot, f), msaa?, motionBlur?, bloomMask? }`。
- `render` 必须是时间的纯函数：只用 `f.t` / `f.lt`，只用确定性种子，不用 `Math.random` 和 `Date`。
- 静态内容在 `create()` 里烘焙；用 `ctx.range` 只建本块需要的子场景。
- 你的镜头 id、帧区间、`transitionIn` 都已写在 `timeline.json` 里。不要改 `timeline.json` 的时间、shots、cards。确需改自己镜头的 post、params、motionBlur、msaa，只改自己镜头那一条，并在报告里写明。
- **预算**：平均每帧 ≤ 1.5 s（含后期），峰值 ≤ 3 s。用 stills 渲染器打印的毫秒数量；第一张含着色器编译，不算。

## 坐标与规则

- R = (734, 540) 是光的接力坐标；C = (960, 540) 只在 [2112, 2892) 使用；P_ans = (1520, 540)。
- 心跳就是光标闪烁：第 k 拍 = 帧 24k，亮 [24k, 24k+12)。
- 宇宙不发声。光比声早 8 帧（声音组负责声音，你只管画面在剧本规定的帧发生）。
- 读字目标的笔画 HDR ≤ 0.4，或用 bloomMask，不让泛光吞掉笔画。

## 工作方法（迭代到真正好看为止）

1. **先快速实现所有镜头的第一版。** 不要留 slate。旧模块里能复用的代码尽量复用：可以 import，也可以复制到新模块里改；但不要改别组的文件。
2. **出静帧**：`node render/render.mjs --stills <t1,t2,...> --stills-dir build/stills/<你的组名> --scale 0.5`，时间单位是全片秒数。
   - 全局信号量最多允许 2 个渲染进程；要等就等，不要杀别人的进程，不要手动删 build/locks。
   - 隔得很远的几个时间点会让渲染范围变大、建场变慢，可以分几次渲染。
3. **用 Read 看每一张图。** 用节日级摄影指导的眼光判断：构图、R 点、曝光、色彩、细节、锯齿、色带、噪点、可读性，是否符合剧本，是否电影化。然后改进。至少做 2–3 轮认真的修改。
4. **逐条对照检查点 K-n**，能量化的就用 python3 + PIL/numpy 量。720p 检查方法：把 1080p 静帧缩到 1280×720 再看。
5. **检查运动与转场**：渲染几帧连续帧，确认平滑、无闪烁；渲染你段落的首帧、尾帧和交接帧。需要看运动时，最多渲染 3 s 的小片段，`--scale 0.5`，放 build/ 下。
6. **最终验证**：每个镜头至少 2 张全分辨率（`--scale 1`）关键帧，记下每帧毫秒数。
7. 不要渲染整片，不要覆盖 build/video.mp4、output/ 或音频。不要 git commit（制片统一提交）。

## 交接帧（长镜头内部，必须像素连续，没有黑场或白场藏切）

| 帧 | 上游 → 下游 | 约定 |
|---|---|---|
| f600 | p_terminal (S06) → a_origin (A1)，match | R 处白点（HDR 1.5，静止）在 f600 自己炸开，与旧版 S06→S07 相同 |
| f1212 | a_origin (A1) → a_star (A2)，handoff | 落在置换①“节点日冕光”[1200, 1224) 的中点。共享代码 `web/src/shots/_corona.js` 由 **A1 组** 编写并先行提交：日冕光的径向剖面、颜色、亮度曲线，都是 t 的函数，按剧本 S02-d。A2 组 import 它，保证 f1212 前后连续 |
| f1692 | a_star (A2) → a_descent (A3)，handoff | 落在置换③“云层”[1680, 1704) 的中点。共享代码 `web/src/shots/_clouds.js` 由 **A3 组** 编写：云层充满画面时的外观，以及相机高度与视野随 t 的变化。A2 组 import 它，用于 [1680, 1692) |
| f1758 | a_descent (A3) → f_fire (A4)，handoff | 落在置换⑤“草叶横扫”[1756, 1762) 之中。共享代码 `web/src/shots/_sweep.js` 由 **A3 组** 编写：金合欢与草叶前景横扫是 t 的函数。f_fire 组 import 它，用于 [1758, 1762)。相机、暮光方向、草堆位置在两侧一致：草堆在 R，暮光在左 |
| f3336 | b_flight 内部 (B1 → B2) | 同一模块，自然连续 |
| f3864 | b_flight (B2) → w_sea (S34)，handoff | 蓝点在 R：4×4 px，x 732–735，y 538–541，核心 #82A4DA，亮度约 160，周围 160 px 无星。两侧逐像素一致；w_sea 从这一点长出字海 |

- 共享代码文件只由指定的组编写；另一组只 import，不修改。需要修改时，在报告里提出。
- 共享文件还没写好时，先用你自己的近似实现，等对方提交后再切换。
- 交接两侧的 `post()` 必须一致（或使用 postBlend），只依赖 f。
- 验证方法：渲染交接帧前后各 2 帧，例如 f1210–1214，确认看不出接缝，并量出差异。

- 改动的文件；
- 最佳静帧路径；
- 检查点逐条结果；
- 交接帧验证结果；
- 共享需求；
- 已知问题；
- 你对剧本做出的必要偏离及理由。
